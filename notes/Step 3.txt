Retrival Augmented Generation (RAG): 
- Optimizing the output of an already trained LLM
- LLMs are already trained on large amounts of data.
- RAG allows an LLM to reference some specific knowledge base for output without retraining the model. 
- Allows LLMS to answer questions better in different contexts. 

LLMS can give false or out-of-date info, RAG is an approach to solving this problem.
It tells the LLM to get info from some specific, pre-determined knowledge sources. 

Steps:
1. Get external data: 
    - This data can come from multiple sources, and be in various forms. 
    - Use an embedding model to convert this data into vectors AI models can understand. 
2. Get relevant info from the external data:
    - Convert user query into vector, and compare to external data vectors. 
    - Uses semantic search.
3. "Augment" LLM prompt
    - We improve the input to the LLM by adding the relevant info to the user prompt.

With this approach, you have to regularly update the external data & the vector embedding representations of it.
Otherwise the external data, and the LLMs responses will become stale.

For this trip planner:
- If I just ask Gemini to invent an itinerary, it can make mistakes such as suggesting generic tourist attractions, places that have closed, etc.
- We want to first retrieve real places from an external source, get the relevant info by ranking them, and provide this list to Gemini.
- So Gemini has the candidate activities already. 

1. Get external data: Real activities in the city potentially from OpenStreetMap. Convert into vector database.
2. Retrieval: Convert user query into vectors, and compare against external data to find the most semantically similar activites.
    - This is not the same as ranking. 
    - Retrieval decides which places we should consider. 
    - Ranking decides which of these places best match the users preferences.
3. Augment LLM query: Provide Gemini with query + relevant info added as context.

normalize_place: Turns an OpenStreetMap record into an Activity object
- From raw data gets: Tags, name, category & lat/long coords.
    - Tags saved using OSM_DETAIL_TAG_KEYS. This stores all the useful tags we want to keep, so we don't keep tags irrelevant to the trip planner. 
- If the place doesn't have all this info it's not viable --> Ignored.
- Otherwise, returns an Activity object.

normalize_places: Turns multiple OpenStreetMap records into an Activity list.
- Uses normalize_place for each record.
- If any record is not viable OR a repeat --> Ignored.

build_overpass_query: 
- Used by fetch_raw_places.
- Uses OSM_CATEGORY_FILTERS to decide which places we will fetch by tag. 
- So if a place doesn't have any of the specified tags: It's not fetched. 
- Limiting, but also good filtering. Probably need to expand.
- nwr: Fetches nodes, ways, and relations from overpass:
    - Node: A single point on a map. Has long/lat. 
    - Way: A line or closed polygon/area. Has an ordered list of nodes. 
    - Relation: More complex structures. Combination of nodes, ways, or other relations. 
    - ex) https://algo.win.tue.nl/tutorials/openstreetmap/#:~:text=A%20node%20represents%20one%20single,ordered%20list%20of%20node%20identifiers.
        - The example shown represents the map with ways and nodes.
        - This would be a relation (pretty sure lol)
